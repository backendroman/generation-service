# Сервис генерации

Принимает заказ на генерацию, списывает токены и отправляет задачу первой подходящей ноге (провайдеру). Провайдер отвечает вебхуком. При отказе задача идет на следующую ногу, если ноги кончились - задача failed и токены возвращаются. Пополнение баланса приходит вебхуком платежки

Python 3.12, FastAPI, asyncpg (SQL руками), Alembic, PostgreSQL 17, pytest

В compose: `app` (uvicorn, 4 воркера), `alpha` и `beta` (фейковый провайдер, один образ), `db`, `migrate` (alembic перед стартом app), `tests` (профиль `test`)

## Запуск

```bash
docker compose up --build
```

Сервис на `localhost:8000`, провайдеры на `:8001` и `:8002`, по умолчанию отвечают успехом через 2-20 секунд

Подпись вебхуков: `X-Signature` = hex HMAC-SHA256 от сырого тела, секрет `WEBHOOK_SECRET` (`dev-secret`)

```bash
BODY='{"payment_id":"pay-1","user_id":"11111111-1111-1111-1111-111111111111","tokens":10,"status":"succeeded"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac dev-secret | sed 's/^.* //')
curl -s -X POST localhost:8000/webhooks/payments -H "Content-Type: application/json" -H "X-Signature: $SIG" -d "$BODY"

curl -s -X POST localhost:8000/generate -H "Content-Type: application/json" \
  -d '{"user_id":"11111111-1111-1111-1111-111111111111","model_slug":"image-fast","prompt":"a cat"}'
curl -s localhost:8000/tasks/<task_id>
curl -s localhost:8000/users/11111111-1111-1111-1111-111111111111/balance
```

### API

| Метод | Путь | Ответ | Ошибки |
|---|---|---|---|
| POST | `/generate` | 202 `{task_id, status}` | 400 нет ноги под столько референсов, 402, 404, 422, 429 |
| POST | `/webhooks/providers/{name}` | 200 `{outcome}` | 401, 404, 422 |
| POST | `/webhooks/payments` | 200 `{credited}` | 401, 409, 422 |
| GET | `/tasks/{id}` | статус, текущая нога, попытки | 404 |
| GET | `/users/{id}/balance` | баланс и последние записи журнала | 404 |
| GET | `/health` | | |

Ошибки в виде `{"error": "<код>", "detail": ...}`. `outcome` у вебхука провайдера: `applied`, `stale`, `duplicate`, `late_accepted`, `late_ignored`

Настройки через env, все есть в `app/config.py` (`PROVIDER_TIMEOUT=60`, `MAX_ACTIVE_TASKS=3` и т.д.)

Фейковый провайдер читает `FAILURE_RATE`, `FAILURE_TYPE`, `DELAY_MIN`/`DELAY_MAX`. Для тестов у него есть `/_control/*`: задать сценарий для задач с подстрокой в prompt, придержать вебхук и отправить его потом руками

## Тесты

Тесты гоняются против поднятого compose (HTTP + БД):

```bash
docker compose up -d --build
docker compose --profile test run --rm tests
```

С хоста: `pip install -e ".[dev]"`, потом `pytest`. `pytest -m "not slow"` пропускает тесты сторожа, они ждут настоящие 60 секунд, весь прогон минуты 4-5. После каждого теста проверяется, что баланс сходится с журналом и что нет задачи одновременно с результатом и возвратом

## Миграции

Только Alembic, SQL руками: `0001` схема с триггерами журнала, `0002` модели `image-fast` и `video-long`. Применяются сервисом `migrate`, вручную - `docker compose run --rm migrate`

Новая миграция: `alembic revision -m "..."` (из контейнера нужно смонтировать `./migrations`, иначе файл останется внутри), дописать `upgrade()`/`downgrade()`, `alembic upgrade head`

## Как сделано

**Деньги.** Баланс меняет только триггер на вставку в `ledger`, напрямую `users.balance` не обновить, журнал append-only. У каждой записи уникальный ключ (`payment:<id>`, `charge:<task>`, `refund:<task>`), так что второе начисление или возврат не вставятся даже при ошибке в коде. Гонки закрыты `FOR UPDATE`: платеж блокирует строку в `payments`, все переходы задачи начинаются с блокировки строки в `tasks`, `/generate` блокирует пользователя (лимит и баланс проверяются под ней). Advisory locks и SERIALIZABLE не брал - первые легко забыть взять, со вторым нужны ретраи везде

**Воркеры.** Состояния в памяти нет. Сторож и диспетчер крутятся в каждом воркере и берут работу через `SKIP LOCKED`. Попытка создается в `pending` в той же транзакции, что и переход задачи, а HTTP к провайдеру идет после коммита (outbox). Если воркер упал до отправки, попытку подберет диспетчер после истечения аренды и отправит с тем же `Idempotency-Key`

**Падение посреди вебхука.** Вебхук обрабатывается в одной транзакции вместе с записью в `webhook_events`, 200 отдается только после коммита. Если процесс упал до коммита, транзакция откатится, провайдер не получит 200 и пришлет вебхук еще раз (а если не пришлет, через `PROVIDER_TIMEOUT` задачу сдвинет сторож). Если упал после коммита, но до ответа, повтор просто получит `stale` или `duplicate`, второго возврата или перехода не будет. Новая попытка к этому моменту уже лежит в базе в `pending`, ее отправит диспетчер любого живого воркера. Если упали между отправкой провайдеру и записью `sent`, попытка уйдет повторно с тем же `Idempotency-Key`, и провайдер вернет тот же `external_id`, не создавая вторую задачу

**Поздний completed (правило 6).** Попытка, по которой сдался сторож, становится `timed_out`. Если по ней потом приходит completed, а задача еще идет на следующей ноге - результат принимаем, текущую попытку помечаем `abandoned`. Если задача уже закончилась (failed с возвратом или completed на другой ноге) - ничего не меняем, ссылку кладем в `late_result_url`, провайдеру отвечаем 200, чтобы не ретраил. Так же обрабатывается синхронный таймаут `POST /tasks` (провайдер мог задачу принять). После явного отказа поздний completed не берем

Почему так: пока задача жива, возврата еще не было, а пользователь уже заплатил, так что отдать ему готовый результат правильно - выкидывать его и ждать следующую ногу, которая может тоже отказать, глупо. После возврата результат отдавать нельзя по условию, а списать токены заново тоже плохо: на балансе их может уже не быть, и итог зависел бы от того, кто успел первым, вебхук или сторож. Поэтому после возврата задача остается failed, а ссылка сохраняется только для разбора

**Прочее.**
- нога подходит, если `len(ref_images) <= max_ref_images`; если ни одной - 400 до списания
- после moderation пропускаются ноги с `skip_on_moderation`, таймаут считается technical
- payload - сразу failed с возвратом, без других ног
- 5xx, 408, 429 и сетевые ошибки при отправке - technical, остальные 4xx - payload
- платеж начисляется только при `succeeded`, тот же `payment_id` с другими данными - 409; неизвестного пользователя платеж создает

Условности: `/generate` не идемпотентен со стороны клиента, `webhook_events` никто не чистит, при `abandoned` провайдеру не отправляется отмена
